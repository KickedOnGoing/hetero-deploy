# 算法分块异构并行部署：可实现性论证

> 目标：为手机 OEM 提供一套「训练用 PyTorch、编译期自动分块、运行时跨 CPU/GPU/NPU 并行执行」的 SDK 与工具链。
> 本文回答一个必须诚实回答的问题：**这个想法在什么条件下成立，在什么条件下必然失败。**

---

## 0. 结论先行

**条件可行，但不是无条件可行。** 把它当成"把模型切几块丢到不同芯片上就会更快"是错的；把它当成"在编译期用代价模型搜索、在运行期用 DAG 调度器执行的一类优化问题"是对的。

必须区分三种常被混为一谈的收益：

| 收益类型 | 来源 | 是否需要真并行 | 本项目实测 |
|---|---|---|---|
| **A. 后端适配** | 把算子放到最适合它的芯片（NPU 做卷积、GPU 做非线性、CPU 兜底） | 否，串行链也有收益 | 主要收益来源 |
| **B. 跨芯片并行** | 分叉后互不相干的分支同时占用不同后端 | **是** | 96×96 样例 `overlap_pairs=1` |
| **C. 跨帧流水** | 第 k 帧在 NPU、第 k-1 帧在 GPU，提高吞吐 | 是（跨帧） | 67 → 99 fps（NPU 主导）、174 → 247 fps（均衡） |

关键判据：**同一时刻一个 NPU 只能执行一个子图**。因此"两个分支都放最快的 NPU"不产生任何并行；只有当它们落到**不同后端**且**公共前驱被显式切开**时，B 才成立。本工具链在分区算法里专门处理了这一点（`build_parts` 的跨后端分叉切分）。

**核心工程价值**其实在于：工具链会**在编译期给出可证伪的判定**。不适合拆的模型，它明确回答"不建议拆"；适合拆的，它给出加速比、理论上界、搬运开销占比和子图理由，而不是让工程师上板碰运气。

## 1. 平台事实（论证的地基）

以下事实直接决定架构选型，均来自公开资料：

1. **MTK 侧主 SDK 是 NeuroPilot 8.0**，适配天玑 9400/9300/8400/8300。公开版提供 NP Converter（PyTorch/TF → TFLite + PTQ）与 TFLite Shim API；**NDA 版（OEM 可获取）**才包含 Neuron SDK：`ncc-tflite --arch=mdla3.0` 离线编译出 `.dla`、`neuronrt` 执行、Neuron Delegate[[1]][r1][[2]][r2]。社区实测在天玑 7300 上可做到 66/66 算子全部上片，但要求 float32 bias、不能是混合精度整型 bias[[3]][r3]。
2. **MTK 官方明确支持异构协同**：NeuroPilot 会"在必要时采用异构运算，结合多个处理器"，并举例 AI-VRS / AI-HDR / 超分中同时使用 GPU 与 APU[[4]][r4]。这说明"多芯片协同"在平台层是被支持的，但注意官方描述的是**任务/流水级协同**，不是单个算子内部的跨片并行。
3. **NNAPI 不能作为新架构的依赖**：自 Android 15 起 deprecated，Google 明确建议迁移到 LiteRT，并宣布 2027 起移除[[5]][r5][[6]][r6]。任何把 NNAPI 当作统一调度层的方案都有明确的生命周期风险。
4. **当前主路径是 LiteRT + NeuroPilot Accelerator**：MTK 与 Google 合作把 NeuroPilot 集成进 LiteRT，提供统一 API、AOT 离线编译、按需自动 fallback[[7]][r7]。
5. **LiteRT 已经把"图分区 + 编译 + 运行时派发"做成了标准抽象**：Compiler Plugin 的 `LiteRtCompilerPluginPartition` / `...Compile` 负责标记可加速子图并生成 context binary；Dispatch API 提供 `async_interface`（异步执行）、`graph_interface`（串联多个 executable）、`GetInput/OutputRequirements`（缓冲区需求协商）、`RegisterTensorBuffer` / `AttachInput` / `Invoke`，以及 `LiteRtEvent`（sync fence fd）做跨加速器同步[[8]][r8][[9]][r9]。**这正是本 SDK 编译产物要对上的接口形状。**
6. **碎片化是已被量化的性能杀手**：一个处于网络中间的 NPU 不支持算子会产生两次跨子图边界搬运；学术界在真机实测中记录到过度分区带来最高 **+28% 延迟**，持续满载 2.5 分钟后热降频带来最高 **4.3× 性能衰减**[[10]][r10]。MTK 自己也提供 `NEURON_FLAG_MIN_GROUP_SIZE` 控制最小 NPU 子图规模[[2]][r2]。
7. **算子级跨片并行有学术与工业先例**：μLayer（通道维切分单层到 CPU+GPU）、CoDL（混合维度切分 + 算子链）、AsyMo（非对称多核 GEMM 分块）、Band（子图 + 动态规划调度）、NN-Stretch（子图空间调度）、Puzzle（2025，遗传算法联合搜索分区/映射/优先级）[[11]][r11][[12]][r12]。结论一致：**可行，但收益强依赖图结构与通信代价**。
8. **零拷贝有前提**：AHardwareBuffer / DMA-BUF 可以让 GPU 与 NPU 共享物理内存，但需要上下游接受相同的 buffer type、layout、stride 与对齐；若 NPU 只吃特定对齐的 AHWB 而 GPU 产出 GL texture，则每帧都要转换一次[[8]][r8][[13]][r13]。有真机记录显示 3.2 ms 的推理伴随约 10 ms 的数据准备/搬运[[14]][r14]。

## 2. 形式化模型与收益判据

设算子图为 DAG $G=(V,E)$，每个算子 $v$ 可绑定到后端 $b \in \{CPU,GPU,NPU\}$，能力表 $A(v,b)\in\{0,1\}$，算子计算时间 $t_c(v,b)$，每张跨片张量 $e$ 的搬运/同步时间 $t_m(e)$，每个子图提交开销 $t_l(b)$。

定义（单位 us）：

$$
\begin{aligned}
T_{seq}   &= \text{单一最优后端方案的离散事件模拟 makespan（含其自身降级搬运）} \\
T_1       &= \sum_{p \in Parts}(t_l + \sum_{v\in p} t_c) + \sum_{e\in E_{cross}} t_m(e) \quad\text{（分区方案顺序执行）}\\
T_\infty  &= \text{分区 DAG 关键路径长度（含跨片边）} \\
T_{par}   &= \text{离散事件模拟 makespan：每后端一条串行队列 + DMA 队列}
\end{aligned}
$$

于是：

$$
S = \frac{T_{seq}}{T_{par}},\qquad
S_{max} = \frac{T_{seq}}{T_\infty},\qquad
T_{par} = T_\infty + \underbrace{\text{资源竞争空闲}}_{\ge 0} + \underbrace{t_m + t_l + t_{sync}}_{\text{切分引入}}
$$

**加速成立的充要条件**：

$$
S>1 \iff T_{seq} - T_\infty > \text{资源竞争空闲} + \sum t_m + \sum t_l + \sum t_{sync}
$$

由此直接推出几条硬结论：

- **链式图（DAG 宽度 = 1）**：$T_\infty \approx T_1 \approx T_{seq}$，右边恒为正，故 $S<1$ 恒成立。工具链对此直接输出 `NOT_RECOMMENDED`，并改推跨帧流水（只提吞吐、不降单帧延迟）。本项目 `ChainNet` 验证了该判定。
- **两分支对称、NPU 有效吞吐为 GPU 的 $r$ 倍**：把一个分支挪到 GPU 后，理想情况下 $T_{par}\approx \max(T_{npu}, r\,T_{npu})$，而 $T_{seq}\approx 2T_{npu}$。忽略搬运时需要 $r<2$ 才有收益；计入搬运/同步后临界 $r$ 明显更小。**NPU 越强，跨片并行越不划算** —— 这是最反直觉但最重要的结论。
- **固定开销必须被摊薄**：$t_l + t_{sync}$ 与模型规模无关，因此小模型必然不划算。本项目 32×32 样例下 `auto` 策略主动选择「整图单 GPU、不拆」，96×96 样例才选择 4 子图异构方案，正是这个效应的体现。

关于基线有一个容易出错的细节：朴素地"把所有算子时间相加"会漏掉单后端方案自己也会因算子不支持而产生的跨片搬运，从而**人为夸大**分区方案的优势。本工具链的 `planner._fair_baselines` 对每种单后端解也执行同样的 `build_parts + simulate`，保证 $S$ 可比。

## 3. 本项目实测结果（可复现）

环境：沙箱 x86 + PyTorch 2.10 + GCC 13；芯片档案为**可配置模板**（`hx/opset.py: DEFAULT_CHIP`），所有数值必须由上板 profiling 回填。运行 `python3 -m examples.export` 与 `runtime/build/hx_run` 复现。

| 场景 | 结构 | 策略 | 子图 | 加速比 | 真并行 | 判定 |
|---|---|---|---|---|---|---|
| 96×96 双分支 | 分叉 + 汇合 | `auto` | 4（NPU/GPU/NPU/GPU） | **2.29×** | 是（overlap=1） | `RECOMMENDED` |
| 32×32 双分支 | 同上，规模小 9× | `auto` | 1（整图 GPU） | 1.00× | 否 | `MARGINAL`：整图单后端最优 |
| 纯链式 | DAG 宽度 1 | `auto` | 1（NPU） | 1.00× | 否 | `NOT_RECOMMENDED` |
| 32×32 强制异构 | 分叉 + 汇合 | `force_hetero` | 4 | 0.57× | 是（overlap=1） | `NOT_RECOMMENDED`（**仅用于验证调度链路**） |

96×96 场景的关键数字：$T_1$=971.9 us、$T_\infty$=623.4 us、理论上界 **2.29×**、实际 **2.29×**（该切分已无资源竞争空闲，达到自身极限）、搬运开销占比 10.0%、跨片边 2 条、DMA 队列占用 91.2 us。C++ 运行时实测 `overlap_pairs=1` 与编译期预测一致，**输出与 PyTorch 逐元素误差 0**。

**峰值内存**（`hx/memory.py` 的共享缓冲槽，静态证明无并发读写冲突）：

| 部署包 | 无复用 | 复用后 | 节省 |
|---|---|---|---|
| 96×96 双分支 | 16.52 MB | **8.26 MB** | 50.0% |
| 32×32 强制异构 | 1.84 MB | 0.92 MB | 50.1% |
| 纯链式 | 1.31 MB | 0.79 MB | 40.0% |

复用条件基于**依赖偏序的 happens-before**（张量 Y 可复用槽 S 当且仅当 S 上所有旧张量的 consumer 都是 Y 的 producer 的祖先），而非拓扑序区间——后者在并行分支上会把「拓扑靠后但同时执行」的两个张量错误复用。`view` 类算子是零拷贝别名，与其根张量共槽。C++ 运行时按 `manifest.memory.slots` 共享缓冲，`verify_buffer_plan()` 与端到端数值校验（误差 0）双重确认安全性。

跨帧流水基准（`hx_bench --frames 64`，纯调度压测）：

| 部署包 | depth=1 | depth=4 | depth=24 | 提升 |
|---|---|---|---|---|
| 96×96 异构（npu/gpu） | 67.4 fps | 93.0 fps | **99.1 fps** | 1.47× |
| 32×32 强制异构（gpu/cpu） | 173.5 fps | 247.4 fps | 247.4 fps | 1.43× |

> 注：纯调度压测（`skip_compute`）下绝对吞吐受 us 级 sleep 精度影响，虚拟延迟放大 20×（`--scale 0.05`）使趋势稳定；**数值仅反映相对提升**，生产性能必须上板测。
> - 修复 `next_frame` 的数据竞争、改用每后端独立队列锁后，两条曲线均**单调饱和**，早期版本的深度突变/非单调现象消失；
> - 均衡后端（gpu/cpu）在 depth=4 即饱和，NPU 主导链因瓶颈链气泡继续缓慢爬升（1.47×），印证 §2「同后端独占串行 / 链不平衡→气泡」；
> - 跨帧重叠数 `overlap_pairs` 随 depth 上升（64 → 212），证明跨帧重叠机制真实有效；
> - 理论吞吐上界由编译期离散事件模拟给出（`plan.pipeline.steady_fps`）。

## 4. 敏感性分析：收益临界条件

`tests/sensitivity.py` 扫描三个参数（结果写入 `build/analysis/`）：

- **NPU/GPU 有效吞吐比 $r$**：`build/analysis/sweep_ratio.csv` 给出 $S(r)$ 曲线与 $S_{max}(r)$，可直接读出 $S=1$ 的临界比值。
- **跨片固定开销** `fixed_cross_us`（固定切分、基线为整图 GPU 零跨片）：开销从 0 增到 250 us 时 $S$ 从 **0.94 单调降到 0.80**，搬运占比从 3.2% 升到 38.0%。基线保持稳定，因此曲线纯粹反映切分的增量开销（同步握手 / layout 转换），对应"零拷贝握手失败"的真实代价。
- **模型规模** `flops_scale`：固定切分下 $S$ 从 **0.57 单调升到 0.98**（上界 0.57→0.98），证明固定开销随规模被摊薄、$S$ 趋近该切分的理论上界。

> 关于固定切分为何 $S<1$：为保证「至少两后端 + 真实时间重叠」，`force_hetero` 会把一支降级到 CPU，其**后端适配损失**使该切分本身不划算——这正是 `auto` 分区会拒绝它的原因，与比例扫描中 `auto` 给出的 **2.55× 峰值加速**形成对照。开销/规模扫描刻意复用这个固定切分，只用来观察两个**单调性**（开销增大 S 降、规模放大 S 升），不用于论证该切分值得部署。

比例扫描还给出一个反直觉但稳健的结论：**某一后端明显更强时 `auto` 收敛到单后端整图（parts=1），只有两端吞吐接近时才拆分并行**；曲线非单调源于启发式搜索在不同配置下的策略跳变，而非模型不稳定（同一方案重复模拟逐位一致，见 `tests/test_core.py`）。

这三张曲线是 OEM 做 go/no-go 决策的依据：**先用目标芯片实测 profile 回填 `chip.json`，再跑一次扫描，就知道这批模型该不该分块。**

## 5. 训练侧如何配合（最大化自由度）

设计原则是**训练与部署彻底解耦**：部署决策 100% 留在编译期，训练代码不写任何部署相关约束。

训练侧可以继续使用：

- Python 控制流（`if/for`，基于 shape 的分支在 `torch.export` 时被自动特化；本项目样例就含 `if x.shape[-1] >= 32`）；
- 任意 `nn.Module` 嵌套、参数共享、自定义 `autograd.Function`；
- 任意 dtype、动态 batch（`dynamic_shapes` 声明）；
- 任意算子：BatchNorm、SiLU、GELU、Softmax、LayerNorm 都在 APU 能力表外，由工具链处理。

训练侧只需提供 **两样东西**：代表性输入 `sample_inputs`（形状特化）、可选 `dynamic_shapes`；量化时再加校准集。

"可部署化"全部由工具链完成：

| 训练侧写法 | 工具链动作 |
|---|---|
| BatchNorm | `fold_batch_norm` 折叠进 conv/linear 权重，减少算子与访存 |
| SiLU / GELU 等 APU 不支持的激活 | 能力表过滤 → 自动放 GPU/CPU；可选 `decompose_silu` 分解为 sigmoid+mul |
| `clone` / `view` / `_to_copy` | identity 消除与视图折叠 |
| 数据依赖的动态控制流 | `torch.export` 报错时给出可操作修复建议（声明动态维度 / 外移逻辑 / 注册 Fake impl） |
| 自定义算子 | 注册 FakeTensor/Meta 后即可被抓取；否则用 `hx.boundary()` 隔离到 CPU 子图 |

**可选标记（软提示，绝不强制）**：`hx.prefer(x, "npu")`、`hx.mark(module, "gpu")`、`hx.boundary(x, name)`。不加标记时编译器全自动；加了标记时编译器先校验算子能力，**非法提示自动忽略**，绝不会导致编译失败。`hx.mark` 的提示会沿 producer 链反向传播到模块内部算子，直到遇到共享分叉点为止。

## 6. 编译与运行时的实现要点

**编译期**（`hx/`）：`torch.export` → FX 降级 HX IR → 重写 → 并行感知局部搜索（目标函数 = 离散事件模拟 makespan，而非"每个算子 individually 最快"）→ 子图构造 → **内存规划（liveness + 共享缓冲槽）** → 双重校验（数值 + 结构）→ 产物生成。

代价模型采用 **roofline 双下界**：单算子耗时 = $\max(t_{flops},\ t_{mem})$，其中 $t_{mem}= \text{读写字节}/\text{片内带宽}$。缺了访存下界，reshape / 逐元素算子会被估成 0 us，分区器会凭空把小算子铺到 NPU 上制造碎片。模拟器把每个后端建模为 `slots` 条串行队列 + 一条 DMA 队列，所有遍历排序，**同一分区方案重复模拟逐位一致**；跨片搬运按**逐张量**累加（早期按 `(src,dst)` 取 max 会漏算同对多张量的传输）。

分区算法里三条容易被忽略但决定成败的规则：

1. **同后端独占串行**：把两个独立分支都放 NPU 不会并行，评价函数必须建模"每后端一条串行队列"；
2. **跨后端分叉切分**：公共主干若和其中一条分支合并，另一条分支要等整条分支跑完，并行机会被"连续段合并"悄悄吃掉。工具链检测"某张量的消费者跨后端"并强制把生产者单独成段；
3. **碎片抑制**：小 NPU 子图用软惩罚（而非强制降级到 CPU —— 那会让计算密集算子瞬间慢一个数量级），对应 `NEURON_FLAG_MIN_GROUP_SIZE`。

**运行时**（`runtime/`）：manifest 驱动、三个后端各一条 worker 队列、DAG 就绪驱动提交、共享缓冲 + owner/fence 语义、跨片边按 `cost_us` 模拟搬运、跨帧流水、全链路时间线。生产落地时只需实现 `IBackend::execute`，调度层零改动。

本轮优化修复了四处会影响结论可信度的实现缺陷：

| 缺陷 | 后果 | 修复 |
|---|---|---|
| 模拟器 DMA 排队依赖 `set` 迭代顺序 | 同一方案重复模拟结果漂移 | 依赖按前驱完成时刻排序、part 商图用确定性拓扑序 |
| `next_frame` 被多个 worker 无锁自增 | 数据竞争，深流水吞吐非单调 | 与帧元数据在同一把锁内推进，错误标志改原子量 |
| 每个张量各分配一块 vector | 峰值内存 = 全图激活之和 × 在飞帧数 | 按 `manifest.memory.slots` 共享，静态证明无冲突 |
| `view` 算子零拷贝别名与 slot 规划冲突 | 多分支网络数值误差 2.3e-3 | 编译期令 view 输出与根张量共槽，运行时仅在 slot 一致时零拷贝 |

修复后：三部署包数值误差回到 **0**，流水基准从"深度突变"变为**单调饱和**，峰值内存下降 40–50%。`tests/test_core.py` 用 11 项断言把这些性质固化为回归测试（含小规模穷举对比，验证 `auto` 不劣于任一单后端且接近全局最优）。

## 7. 风险清单与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 算子能力缺口 → 子图碎片化 | +28% 延迟（实测[[10]][r10]） | 能力表 + 最小子图规模 + 软惩罚；训练侧改写或 `boundary` 隔离 |
| NPU/GPU layout / 对齐不一致 | 每帧转换，零拷贝失效 | `tensor_requirements.json` 需求握手，上板前验证 buffer type 交集 |
| 量化一致性（INT8/FP16 vs FP32） | 精度漂移 | 校准集 + 逐子图数值校验 + 混合精度边界显式声明 |
| 热节流、与 ISP/渲染争用 GPU | 最高 4.3× 衰减[[10]][r10] | 热感知动态降级、后端优先级、运行时 fallback 到单后端 |
| 多后端并发的优先级/抢占 | 尾延迟抖动 | 运行时保留 deadline 与优先级接口（当前原型未启用） |
| 缓冲复用在并行分支上串数据 | 静默数值错误 | happens-before 静态证明 + view 共槽 + 端到端逐元素校验（误差 0） |
| 峰值内存超出设备预算 | OOM / 被系统回收 | 编译期 `manifest.memory.peak_total_bytes` 可核对，运行时按 slot 共享 |
| SDK 需 NDA、与 SoC 版本绑定 | 交付/OTA 复杂 | 抽象 `IBackend`；编译产物按 SoC 型号分发，运行时能力探测 + 降级 |
| NNAPI 生命周期 | 2027 移除[[5]][r5] | 不依赖 NNAPI，走 LiteRT Compiler Plugin / Dispatch |
| 动态 shape / 自定义 op | 导出失败 | 多 shape 特化、Fake impl 注册、图外前/后处理 |

## 8. 生产落地路线与验收标准

**Phase 0 — 校准**：在目标天玑机型上用 `neuronrt` / LiteRT benchmark 测出各后端的有效吞吐、launch 开销、跨片搬运带宽，回填 `chip.json`。**没有这一步，任何加速比数字都没有意义。**

**Phase 1 — 基线**：整图走 LiteRT `CompiledModel(Accelerator.NPU)` / NP8 Converter，建立单后端基线。

**Phase 2 — 分块**：`hx-compile` 生成子图 → NP Converter / `ncc-tflite --arch=mdla3.0` 编译 NPU 子图 → Dispatch API 异步执行 → DMA-BUF/AHardwareBuffer 共享张量 + `LiteRtEvent` fence 同步。

**Phase 3 — 流水与自适应**：启用跨帧流水、热感知调度、能力探测与动态降级。

**Phase 4 — 规模化**：多模型/多任务统一调度、模型 OTA、A/B 与回放。

**验收标准（建议）**：
1. 逐子图与端到端数值误差 ≤ 量化容差；
2. 单帧延迟相对单后端基线改善 ≥ 15%（否则不拆）；
3. 持续 30 分钟满载无热降频导致的性能塌方；
4. 任一后端初始化失败时 100% 可降级到 CPU；
5. 跨片边界数量与 layout 转换次数在上板 profile 中可核对，与 `tensor_requirements.json` 一致；
6. 峰值内存不超过设备预算，与 `manifest.memory.peak_total_bytes × 在飞帧数` 一致。

## 9. 本原型的边界（诚实声明）

- 沙箱没有 MTK 硬件与 NDA SDK，因此 NPU/GPU 后端是**参考后端**：真实执行 IR 算子（保证数值正确）+ 注入代价模型估计时长（保证调度可观测）。它验证的是**编译、分区、调度、同步、流水、校验**这条链路的完整性与正确性，**不是**目标芯片的性能数字。
- 芯片档案、算子能力表是模板，必须由 OEM 用实测数据替换。
- `force_hetero` 是验证/研究模式，明确标注不参与生产裁决。
- 生产对接接口骨架见 `docs/05_MTK生产对接.md` 与 `runtime/backends/ADAPTERS.md`。
